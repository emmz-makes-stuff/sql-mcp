# §3 done: describe_object

<!-- Section: 3 · Tasks: 3.1–3.5 · Base: e1ec1cd -->

Built `ObjectName` (ScriptDom parsing), `NameResolution` (the not-found and ambiguous messages), `ObjectDetails` and
its parts in `CatalogModel.cs`; `ICatalogReader.ResolveAsync`/`DescribeAsync`; their SQL Server queries in
`SqlServerCatalogReader`; `SqlServerTypeNames`; `ToolPipeline.DescribeObjectAsync`; the `describe_object` tool;
and `ObjectDetailsResponse`.

Emmz's answers (2026-10-27, asked before the commit):
- **Unresolved names are audited** as failed `introspection` events with the new `FailureKind.UnresolvedName`
  (`unresolved_name`). The message for the agent names the candidates; the log keeps only the kind.
- **Name lookup follows the database's collation.** On a case-sensitive database `dbo.order_archive` doesn't find
  `dbo.Order_Archive` (unlike `list_objects`, which ignores case). §4.4's chosen objects resolve the same way.
- **A third "unavailable" reason, `clr`,** for CLR routines, which have no T-SQL definition. Design I3 listed only
  `encrypted` and `no permission`.
- **Sequence values are strings**, as the query tools give bigint and decimal values: a `decimal(38)` bound won't
  fit a JSON number exactly.

Other decisions (no behaviour question, so not asked):
- **Name parse errors are refused before the database lookup and aren't audited**, like an unknown type filter.
  Three- and four-part names get "names another database or server".
- **`ObjectName.TryParse` uses ScriptDom while living in the engine-neutral model.** ScriptDom also parses the
  `"schema"."name"` form PostgreSQL uses. Revisit for v2 if it doesn't fit.
- **`ResolveAsync` resolves every name and reports every failure**, one per line, and drops duplicates. Only tests
  call it until `script_database` (§4.4). `DescribeAsync` resolves on its own connection, through the same code.
- **Extras the spec doesn't require, because the queries are per object and cost nothing more:** views also get
  indexes and triggers when they have them; table-valued functions get their result columns. A function's `kind`
  is `scalar`, `inline_table_valued`, `table_valued` or `clr`, and `return_type` is `table` for table-valued ones.
- **A T-SQL parameter's `has_default` comes from parsing the definition** (`SqlServerCatalogReader.ParameterDefaults`),
  because `sys.parameters.has_default_value` is set only for CLR routines. It is null when the definition is
  unavailable (encrypted) or doesn't parse.
- **Indexes leave out the ones behind the primary key and unique constraints** (they're under those parts), and the
  partitioning column SQL Server adds to a key with key ordinal 0. A columnstore index lists all its columns.
- **Types are written as declared:** `nvarchar(200)` (bytes ÷ 2), `(max)`, `decimal(p,s)`, `datetime2(n)`,
  `vector(n)`; user types as `schema.name`. Defaults, check and computed expressions are as SQL Server stores them,
  such as `(sysutcdatetime())` and `([email] like '%@%')`.
- **The list-only timeout advice** ("filter by schema, type or name") is now passed in by `ListAsync`, so a describe
  timeout doesn't suggest filters.
- **The synonym target is unbracketed:** `[dbo].[users]` becomes `dbo.users`.

Gotchas found by probing a SQL Server 2025 container:
- A login with EXECUTE but no VIEW DEFINITION sees the object, a `sys.sql_modules` row with a NULL definition, and
  `IsEncrypted = 0`: that's the `no permission` case. `DENY VIEW DEFINITION` hides the object entirely.
- `OBJECTPROPERTY(..., 'IsEncrypted')` is NULL for database triggers (they're not in `sys.objects`), so an encrypted
  database trigger reports `no permission`. Known, rare, accepted.
- Table types' constraints and indexes are under `sys.table_types.type_table_object_id`, so table types share the
  table queries.

Known gaps: the CLR paths (`clr` reason, CLR parameter defaults, CLR types with no base type) aren't tested, because
the container has CLR off and the seed holds no assembly. The reader's real timeout path is still untested (as in §2).
