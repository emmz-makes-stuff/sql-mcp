# §2 done: classifier, command statements

What landed:
- **Command allowlist:** now `[.. Query, <DML nodes>]` in `Allowlists`. The DML nodes are the targets,
  `OutputClause`, `OutputIntoClause`, `DeleteMergeAction` and `NextValueForExpression`. Table hints aren't
  kind-checked outside a query, so locking hints are allowed in a command.
- **`SideEffectChecks`, per category:**
  - The rowset functions (OPENQUERY, OPENROWSET and its variants, OPENDATASOURCE) are rejected in every category,
    with their own reason ("… reaches outside the database, so no tool runs it"). A guard test checks that no
    allowlist contains them.
  - **WHERE rule:** checked on `UpdateStatement`/`DeleteStatement`. The reasons are "UPDATE needs a WHERE clause at
    line L, column C" and "DELETE needs a WHERE clause at …". `WHERE CURRENT OF` still fails on `CursorId`.
  - **Names rule:** applies in command, ddl and execute. It rejects a `SchemaObjectName` with a database or server
    part, and a column reference of four or more parts. The reason is "writes may only name objects in the target
    database: <name> at … has a database or server part". Queries are unchanged.

Emmz's rulings (2026-10-26):
- **CTE targets are exempt from the WHERE rule.** The spec's "CTE and OUTPUT" scenario contradicted the rule. Her
  choice was to exempt an UPDATE/DELETE whose target is a CTE of the same statement, because the CTE does the
  filtering. Two other options were rejected: requiring a WHERE or TOP in the CTE, and rewriting the scenario. The
  spec requirement now says so, and a new "Update through a filtering CTE" scenario was added. Design W5 is
  updated too.
- **OUTPUT INTO a table only.** "or table variable" was dropped from the spec, because `DECLARE` is rejected, so no
  table variable can exist. A row checks that `OUTPUT … INTO @ids` stays rejected (`VariableTableReference`).
- **Inline VALUES tables are on the query allowlist.** `InlineDerivedTable` and `RowValue` moved to the query list,
  so `SELECT … FROM (VALUES …) AS v (a, b)` is a valid query, and command inherits it for MERGE … USING (VALUES …).
- **Known gap: a three-part scalar function call in a write.** `otherdb.dbo.fn(x)` gets past the names rule,
  because it's indistinguishable from `n.c.value()`-style method calls. She accepted it and asked for it to be
  documented. It's now in the design's Risks. **Task 3.4 must put it in `docs/classifier.md`.**
- She kept the new rowset reason wording.

Test changes outside the table: the wrong-tool examples now carry a WHERE, because a bare `DELETE FROM t` is
rejected outright.
- `ClassifierTests.Wrong_tool*` use `DELETE FROM t WHERE id = 1`.
- `ToolPipelineTests.Rejected_statement` uses `DELETE FROM dbo.users WHERE id = 1`.
- `ServeTests.Rejected_statement` uses `… WHERE 1 = 1`.

Notes for §3:
- The names rule already covers ddl and execute, through the `IsWrite` category check. 3.3 only adds the
  `sys`/`sp_`/`xp_` rule and the parameter shapes. The rows `DROP TABLE otherdb.dbo.t`, `EXEC app.dbo.p` and
  `EXEC remote.app.dbo.p` are already in the table.
- 3.1 walks a view's SELECT under the query category. Since queries may read other databases, a view could read
  one too. That's consistent with the spec (the names rule covers the view's own name only), but mention it in 3.4.
- `NEXT VALUE FOR` is still off the query list, so a `DEFAULT NEXT VALUE FOR seq` constraint would be rejected
  under 3.1's "scalar-expression allowlist" unless that is decided otherwise.
