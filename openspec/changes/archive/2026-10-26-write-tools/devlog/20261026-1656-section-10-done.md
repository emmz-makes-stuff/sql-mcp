What landed:
- **10.1, outcome unknown:**
  - New `FailureKind.OutcomeUnknown` (audit `kind: outcome_unknown`) and `WriteMessages.CheckBeforeRerun`
    ("Check with query before running it again.").
  - Probing first confirmed the bug. A procedure doing `BEGIN TRAN … COMMIT; COMMIT` or `ROLLBACK; INSERT` raised
    266, and the agent was told "nothing was committed" while the row was kept. `COMMIT; BEGIN TRAN` raised no
    error, but `CommitAsync` threw `InvalidOperationException` ("This SqlTransaction has completed"), which escaped
    to the pipeline's "nothing was committed".
  - The executor now:
    - catches a `SqlException` carrying 266, 3902 or 3903, first among the catches (ahead of the cap and timeout
      ones);
    - wraps `CommitAsync`: `InvalidOperationException` means the transaction ended, and `SqlException` means "the
      commit failed, so sql-mcp can't tell whether the batch was committed";
    - no longer calls `transaction.DisposeAsync()` after the commit, so nothing can fail the call once the commit
      has returned. The connection's disposal cleans up.
  - The pipeline's catch-all comment now states that guarantee.
  - README (all or nothing, and the audit paragraph), `docs/classifier.md` and the design's Risks entry are updated.
  - Tests:
    - `SqlServerWriteExecutorTests.A_procedure_that_ends_the_transaction_leaves_the_outcome_unknown`, three cases,
      each checking the row was kept;
    - `ToolPipelineTests.A_write_whose_outcome_is_unknown_is_not_reported_as_rolled_back`.
  - **Untested:** the "commit failed" `SqlException` path (#6). A network drop mid-commit can't be staged reliably
    against the container. Also, only `SqlException` and `InvalidOperationException` from the commit are caught;
    any other type would still reach the pipeline's "nothing was committed". SqlClient wraps transport failures as
    `SqlException`, so that should be rare.
- **10.2, the names rule for a view's SELECT:**
  - `SideEffectChecks.Check` takes `targetDatabaseOnly` in place of the old `IsWrite(category)`.
  - The ddl visitor walks a view's SELECT twice: as a query, which keeps the "the view's SELECT is not a valid
    query: …" prefix, then with `targetDatabaseOnly: true`, whose reason is the plain names-rule one.
  - That way the agent isn't told a valid query is invalid.
  - Covered by four table rows: CREATE, ALTER over a linked server, CREATE OR ALTER with a join, and an EXISTS
    subquery.
  - The delta spec has the requirement sentence plus the "View reading another database" scenario.
    `docs/classifier.md` and the design's Risks entry are updated.
- **10.3:** `OwnCallHint` skips a match right after `GRANT`, `DENY`, `REVOKE` or a comma. Covered by 3 no-hint
  cases.
- **10.4:**
  - `ExistsPredicate` and `SubqueryComparisonPredicate` moved from `Scalars` to the query list, next to
    `ScalarSubquery`. Command still has them, through `.. Query`.
  - ScriptDom itself refuses subqueries in a CHECK ("Subqueries are not allowed…"), so the entries really were dead
    for ddl, and no table row can reach them. I dropped the two rows I'd tried.
  - The ddl description, the schema's `maxAffectedRows` description and the README cap bullet now say TRUNCATE
    TABLE and DROP aren't limited by the cap.
- **10.5:** `SqlTool` (name, category, group, mode, returns rows, method) and `SqlTools.All` in `ToolPipeline.cs`.
  - They replace `CategoryGroups`, the catalog's write-tool tuple array, and the hard-coded paging check.
  - `ToolCatalog.Describe(tool, …)` maps a category to its description.
  - No test changed, and all pass.
