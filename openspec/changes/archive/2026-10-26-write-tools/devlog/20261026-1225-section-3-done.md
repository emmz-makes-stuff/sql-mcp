# §3 done: classifier, DDL and execute

<!-- Base 1db861c · gates green -->

What landed:
- **`Allowlists`:**
  - The new `Scalars` set holds names, literals, scalar expressions and predicates, with no subqueries. `Query` is
    now `[structure…, .. Scalars, ScalarSubquery]`, and `Ddl` starts with `.. Scalars`.
  - `StatementCategories` gains these DDL statements:
    - the ALTER TABLE forms: alter column, drop element, and [NO]CHECK CONSTRAINT;
    - CREATE, ALTER and DROP INDEX;
    - CREATE, ALTER, CREATE OR ALTER and DROP VIEW;
    - CREATE and DROP SCHEMA;
    - CREATE, ALTER and DROP SEQUENCE.
  - The node types were added row by row: default, CHECK and FK constraints, identity options, sort-order
    columns, `IndexDefinition`, `DropIndexClause`, `ViewOption`, `StatementList`, the sequence options, and
    `NextValueForExpression` for sequence-backed defaults.
- **View SELECT:** walked under the query category. The visitor overrides `ExplicitVisit(SelectStatement)` in
  ddl, and the reason is prefixed "the view's SELECT is not a valid query: …".
- **`SideEffectChecks`:**
  - CREATE SCHEMA with AUTHORIZATION, or with elements, is rejected.
  - The system-procedure rule: the `sys` schema, or a name starting `sp_`/`xp_`, ignoring case.
  - An EXEC parameter value must be a `Literal` or a negated numeric literal.
  - `EXEC @rc = …` is rejected.
  - 3.5: the WHERE reasons now read "UPDATE/DELETE needs a WHERE clause that picks the rows to change (at line L,
    column C)".
- **`Phrases.Unsupported`:** create, alter and create-or-alter of a procedure, function or trigger get "…:
  procedures, functions and triggers can't be created through sql-mcp: their bodies run later, unseen by the
  classifier". DROP PROCEDURE and the security DDL keep the generic "… is not supported by any tool".
- **`AllowlistGuardTests.NeverRun`:** checks that programmable and security statements stay out of
  `StatementCategories`.
- **`docs/classifier.md`:** the new "Write categories" section covers what each category accepts, the WHERE,
  names and system-procedure rules, programmable objects, and the procedure trust gap (NOCOUNT, a procedure's
  own ROLLBACK/COMMIT). "Known gaps" now includes the three-part scalar function call. Every full-statement
  example is a table row; this was checked with a grep loop.

Emmz's rulings (2026-10-26), all kept as recommended:
- Defaults may use `NEXT VALUE FOR`.
- `ALTER SCHEMA … TRANSFER` is rejected, because ownership chaining can change who may use the object. The spec
  DDL requirement and design W5 now say so.
- `ALTER TABLE … [NO]CHECK CONSTRAINT` and `ALTER INDEX … REBUILD | REORGANIZE | DISABLE` with no WITH options
  are accepted. Design W5 says so.

Gotchas:
- The parser itself refuses expressions as EXEC parameter values (`1 + 2`, `-(-1)`, `GETDATE()`) and three-part
  view names, as syntax errors. Those rows were dropped, so the parameter check only matters for variables.
- `CREATE SCHEMA x` carries an empty `StatementList` node at line -1, which is why `StatementList` is on the ddl
  list.
- xUnit dislikes duplicate theory rows, so two rows with the same SQL need distinct SQL.
