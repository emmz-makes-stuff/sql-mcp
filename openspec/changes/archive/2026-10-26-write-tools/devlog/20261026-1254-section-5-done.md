# §5 done: write execution

<!-- Base 2006df8 · gates green -->

What landed (design W1–W4):
- **`IQueryExecutor.ExecuteAsync(connectionString, sql, BatchMode mode, limits, ct)`.**
  - `BatchMode` is `ReadOnly` or `Write`. The pipeline's `QueryAsync` passes `ReadOnly`.
  - `FakeExecutor` records `Modes`, and one pipeline test asserts that `query` runs `ReadOnly`.
- **Outcome types:**
  - `QuerySucceeded.RowsAffected` (`IReadOnlyList<int>`, an init property defaulting to empty) is set only for
    writes.
  - `QueryFailed` gains the init properties `Cap` (int?) and `Affected` (long?), set only for the new
    `FailureKind.AffectedRowsCap`, which serialises as `affected_rows_cap`.
- **Write mode in `SqlServerQueryExecutor`:**
  - It runs `SET XACT_ABORT ON` as a separate command before `BEGIN TRAN`.
  - `StatementCompleted` adds each count to the list. Once the total passes the cap, `command.Cancel()` is called
    inline.
  - If the cap was passed, the call returns `CapFailed`, whether or not an exception came. Otherwise it commits.
  - The commit is not cancellable, and runs only once the reader has closed cleanly.
  - Every write error message ends with "The batch was rolled back, so nothing was committed." Timeouts have their
    own write wording.
- **Drain (W3):**
  - `BufferAsync` takes the mode. After a row or byte cap, a write keeps calling `ReadAsync`/`NextResultAsync`
    without fetching values.
  - Later result sets are skipped, not listed as empty sets.
  - The write truncation message says the rest was discarded and the batch still ran to completion.
- **Tests:** `SqlServerWriteExecutorTests` (new, 14 tests) covers:
  - the success case, including what a second connection sees;
  - a part-way PK violation, where a `WAITFOR` after it shows that XACT_ABORT stopped the batch;
  - a conversion error, and a timeout;
  - a large `OUTPUT`, and a byte cap drained through a second statement;
  - over and within the cap, and a two-statement cap;
  - a cap with a flush that stops later statements;
  - an `OUTPUT` clause, a procedure's result set, and a procedure's `SELECT` counting towards the cap.

  Procedures are created through the fixture, not the executor. The existing executor tests changed only to pass
  `BatchMode.ReadOnly`.

Emmz's rulings (2026-10-26):
- **A procedure's SELECT counts.** A `SELECT` reports its count exactly like a DML statement, and SqlClient doesn't
  say which kind of statement a count came from. So `execute` counts selected rows in `RowsAffected` and towards
  the cap (`EXEC` of update 2 + select 2 gives `[2, 2]`). This is recorded in:
  - design W4 and Risks;
  - the spec's cap requirement, with a new scenario, "A procedure's SELECT counts";
  - task 6.4, whose `execute` description must say the cap counts every row count the server reports, including
    rows a procedure's `SELECT` returns.
- **Kept as built:** the error wording (so 6.3 must not add "nothing was committed" a second time), the drain
  behaviour and its message, and the non-cancellable commit.

Gotchas (all verified with a throwaway probe test, since deleted):
- **`command.Cancel()` from another thread (`Task.Run`) does nothing useful.** It blocks on the parser until the
  batch ends. Called inline in the `StatementCompleted` handler, it stops the batch at once ("a severe error
  occurred on the current command"), and that error is caught by `catch (SqlException) when (overCap)`.
- **Counts reach the client only when the server flushes output**: a full packet, or the end of the batch. Small
  output sits in the buffer, so a batch with little output (`INSERT; INSERT; WAITFOR; INSERT`) runs in full before
  any count arrives, and only the rollback saves it. The test uses `RAISERROR('flush', 0, 1) WITH NOWAIT` to
  force a flush. Design W4 now qualifies "later statements never run". This matches the README advice planned for
  6.5 (keep `timeoutSeconds` short).
