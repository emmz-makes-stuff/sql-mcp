# §4 done: wrong-tool reasons per database

<!-- Base 393b35b · gates green -->

What landed (design W6):
- `ClassificationResult.ForTool` keeps its shape. The reason for a category not in `withTools` now reads
  "classified as X; the X tool is denied on this database".
- `ToolPipeline.AllowedCategories(db)` builds the set from a private `CategoryGroups` map (category → group) and
  `db.IsAllowed`. `QueryAsync` passes it instead of the static set. §6's `RunAsync` can reuse the map when it needs a
  category's group.
- `ToolCatalog.Categories` and its `using SqlMcp.Classification` are gone.
- Tests:
  - `ToolPipelineTests.Wrong_tool`: command is allowed on the target, so the reason is "use the command tool".
  - `ToolPipelineTests.Right_tool_is_denied_here`: command is allowed only on a *second* database. This checks
    that the reason follows the target database, not "allowed somewhere". It also keeps the old audit assertions.
  - `ClassifierTests` and the `ServeTests.Rejected_statement` integration test now expect the new wording. The
    integration test runs on default grants, so command is denied there.
- `docs/classifier.md` step 4 describes the per-database set.

Not changed: `openspec/specs/statement-classification/spec.md` still has the old "no command tool yet" scenario.
The change's delta spec replaces it at archive, so don't edit it by hand.
