# §7 done: code-review fixes, correctness

<!-- Section: 7 · Tasks: 7.1–7.6 · Base: d36a202 -->

The seven correctness findings from `code-review` are fixed (rulings in `20261028-1226-section-7-start.md`).

- **7.1 Arguments after the checks.** `RunIntrospectionAsync` now takes a `prepare` step that returns an
  `IntrospectionCall<T>` (the audit request and the read) or an error. It runs after audit-ok, database, grant and
  availability. A bad argument on a denied database is audited as `denied`; with the audit log unavailable, the
  refusal comes first. `ObjectTypes.TryParse` takes null, and `NotAType(null)` says `'null' is not an object type`.
- **7.2 Foreign keys** are grouped by `fk.object_id` and sorted by name, then the declaring table, then the id.
  Sorting by id alone differed between databases and failed the round trip.
- **7.3 Object and type with the same name.** `ObjectName` gains `Type` (init), and `ToRequest()` shows it as
  `dbo.address (table_type)` in the audit log. `ResolveSql` has `AND (@type IS NULL OR type = @type)`. When every
  candidate has the same schema, the ambiguity message says "an object and a type with the same name. Give its
  type too, such as table_type". `describe_object` has `type`. In `script_database`, `objects` is `JsonElement[]`,
  and `ToolCatalog.WithObjectsItemsSchema` patches its items to `oneOf: [string, {name, type?}]` with
  `additionalProperties: false`. `ParseObjectsEntry` refuses numbers, a missing name, extra keys and non-string
  types. Spec deltas: schema-introspection "describe_object tool", and creation-script "Scripting chosen objects"
  (two scenarios). `list_objects` now sorts by schema, name, **type**: the clash made the order nondeterministic.
- **7.4 Encrypted views' triggers** are left out of the whole-database script. The new reason is
  `Completeness.OnEncryptedView` (`on an encrypted view`), found through the trigger's `Parent`.
- **7.5 Chosen tables' triggers.** `InventoryItem.Parent` (from `objects.parent_id`, joined in `InventorySql`), and
  `Completeness.Narrowed` keeps the chosen objects plus their own DML triggers. This closes §5's accepted gap;
  README updated.
- **7.6 Encrypted database trigger.** The probe found a signal, so there was no stop: `sys.sql_modules` documents a
  NULL definition as "encrypted", and otherwise only a login without VIEW DEFINITION sees NULL. The
  `EncryptedDatabaseTrigger` fragment is a NULL definition **and**
  `HAS_PERMS_BY_NAME(NULL, 'DATABASE', 'VIEW DEFINITION') = 1`. It's used in `InventorySql` (rows with no schema)
  and `DefinitionSql` (as the `OBJECTPROPERTY` fallback). An itest covers both.

Seed: a new `crm` schema holds table `crm.address` and table type `crm.address`, and `crm.returns` and
`archive.returns` hold `fk_returns_orders`, both referencing `archive.orders`. The round trip now passes the type to
`ObjectName`. `design.md` I3, I5 and I7 and the README are updated.

Emmz accepted, before the commit (2026-10-28): the `on an encrypted view` reason; the VIEW DEFINITION rule for
database triggers; invalid arguments refused unlogged, as an unknown database is; strict `objects` entries; and both
sort fixes.

Gotcha: the generated schema for a nullable array parameter has `"type": ["array", "null"]`, not `"array"`.
