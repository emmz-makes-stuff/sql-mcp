# §15 Review fixes: memory bounds — done

<!-- Section: 15 · Tasks: 15.1–15.2 · Base: a5dc750 -->

What landed:
- **15.1, byte cap per value.**
  - The executor opens the reader with `CommandBehavior.SequentialAccess`. `SqlServerValues.ReadRowAsync` reads a
    row against the remaining budget and returns null as soon as it can't fit. The row is then not buffered, and the
    result is truncated with the existing byte-cap message.
  - Only columns that can hold more than 8000 bytes are streamed: `varchar/nvarchar/varbinary(max)`, `text`,
    `ntext`, `image`, `json`, `xml` and CLR UDTs. Everything else is read whole and then measured.
  - Text and `json` use `GetTextReader`, binary and UDTs use `GetStream`. Reads go in 8 KB chunks with pooled buffers.
  - The cap counts unescaped UTF-8 bytes. Strings count their text without quotes or escapes, binary counts its
    base64 length (at most `budget / 4 * 3` raw bytes fit), NULL counts 4, and other values count their JSON text.
  - `BoundedText` collects text against the budget. It counts a surrogate pair split across appends as 4 bytes
    itself, because `Encoder.GetByteCount` doesn't carry state between calls. A unit test caught this.
  - design.md's memory risk row is corrected.
- **xml (2026-10-26 decision).** Every SqlClient text accessor either refuses `xml` (`GetTextReader`,
  `GetFieldValue<TextReader>`) or reads it whole (`GetChars`, with ~17 MB allocated for an 8 MB value, even with many
  small nodes). `SqlServerXml` rebuilds the text from `GetXmlReader`, with text content read through
  `ReadValueChunk`. The output follows SQL Server's own serialisation, which a probe established:
  - an element with no content is written `<a/>`;
  - attributes escape `& < > "` plus `\n \t \r`, as `&#x0A;`, `&#x09;` and `&#x0D;`;
  - text escapes `& < >` and `\r`;
  - a text node of only whitespace has its last character written as a character reference (`&#x20;`);
  - CDATA comes out as escaped text, and comments and processing instructions as they are.

  XmlWriter was tried first and rejected: it writes `<a />` and its own entity forms.
  `An_xml_value_matches_SQL_Servers_own_text` compares the output with `CAST(@x AS nvarchar(max))`.
- **15.2, 20 handles.** `ResultStore.MaxHandles = 20`, with the least recently used evicted on `Open`. The store
  orders handles by a use counter rather than the clock, so uses in the same tick still have an order. A result that
  fits on one page takes no slot. The spec scenario "Too many open results" is added.
  - The unknown-handle message now says "...or when more than 20 results are open".
  - The `next_page` tool description now says that only the 20 most recently used handles are kept.

Emmz's answers (all were the recommended options):
- An over-budget value truncates the result before its row. Values are streamed in chunks and stop at the budget.
  Counting is raw text without quotes. The shared unknown-handle message is extended.
- xml is rebuilt through XmlReader rather than read whole.
- Choices put to her before the commit, all kept:
  - the `next_page` description change;
  - the xml parser still reads a single attribute, comment or processing instruction whole (accepted and documented
    in design.md);
  - the allocation-based itest assertion, which measures process-wide allocation, so there's a small flake risk;
  - synchronous reads for fixed values and xml under SequentialAccess.

Gotchas:
- After a sandboxed build, a leftover compiler server can make `make gates` fail with `BUILD_EXIT:1` (CS2012: can't
  open `obj/Release/.../SqlMcp.dll` for writing). Run `dotnet build-server shutdown` and rerun.
- The json type only accepts an object or an array, so a bare `"..."` literal is a SQL error.
- `GC.GetTotalAllocatedBytes` is process-wide. If `A_value_larger_than_the_cap_is_not_buffered` ever flakes, move it
  to a non-parallel collection.

Self-review against the spec found and fixed three things:
- every text and binary cell was being streamed with an 8 KB buffer (now max/LOB only, with pooled buffers);
- `ChunkSize` was duplicated;
- the surrogate count was wrong.
