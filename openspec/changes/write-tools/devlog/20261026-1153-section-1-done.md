# §1 done: affected-rows cap in configuration

<!-- Base 49514d9 · gates green -->

`maxAffectedRows` (default 1000, integer 1 to 2147483647) now goes through the same path as the other limits:
- the schema, `LimitSettings`, `ConfigLoader.MapLimits` and `EffectiveLimits`;
- the resolver's `ProjectLimit` layering, where raising it is a widening;
- `approve`'s diff;
- `config show`'s limits line ("…, 30 s timeout, 1000 affected rows per write");
- `list_databases`' `limits.max_affected_rows`;
- the README sample config.

Nothing enforces it yet. That's §5 (W3).

Decisions (both put to Emmz before the commit, and she kept both):
- **`config show` wording:** the line ends "N affected rows per write".
- **Query tool description:** `ToolCatalog.Query` lists "Databases with other limits", and that check now ignores
  `MaxAffectedRows` (`SameQueryCaps`). Without this, a database that only changed the write cap would be listed
  there with the default query caps text. Each write tool states the cap in its own description (§6.4).

Tests added:
- loader: `maxAffectedRows` read; 0 and 2147483648 rejected with their path;
- loader: `The_readme_sample_config_loads` parses the README's first `jsonc` block. There was no README sample test
  before this;
- resolver: the project raises the cap (applies only when approved) and lowers it (applies without approval);
- pipeline: "Affected-rows cap is listed", and an unapproved raise shows in `not_approved`;
- catalog: a database with only another write cap isn't named in the query description.
